Enrollment takes a machine with nothing on it and ends with scheduled Borg backups that
appear on the portal's dashboard. You fill in a form in the portal, run one command on the
machine, and paste one line on the backup server.

**Supported so far:** Debian 11+, Ubuntu 22.04+, and Proxmox VE 7+ (anything with `apt`
and systemd). Other Linux distributions can follow the [manual walkthrough](#option-b),
replacing the `apt` step with their package manager. Windows isn't supported yet; see
[WINDOWS_CLIENTS.md](WINDOWS_CLIENTS.md).

<a id="what-it-sets-up"></a>
## What enrollment sets up

On the **client**:

| What | Where | Why |
|---|---|---|
| `borgbackup` + `borgmatic` | apt packages | the actual backup tools |
| This host's SSH key for the backup server | `/root/.ssh/haven_borg_ed25519` | generated on the client, so the private key never leaves it |
| borgmatic config | `/etc/borgmatic/haven.yaml` (mode 600) | a separate file, so an existing `/etc/borgmatic/config.yaml` is never touched and borgmatic's own default timer never picks it up |
| systemd service + timer | `/etc/systemd/system/haven-backup.{service,timer}` | runs `borgmatic --config /etc/borgmatic/haven.yaml create --stats` on your schedule (±15 min random delay, catches up after downtime) |
| The portal's "Backup now" key | one line in `/root/.ssh/authorized_keys` | forced to run exactly the `create` command above and nothing else |
| Enrollment state | `/etc/haven-backup/enrollment.env` (mode 600) | lets the script resume if interrupted |

On the **portal**: an SSH credential `<name>-portal-access` (for "Backup now"), a client
host `<name>`, and a repo `<name>` with your retention settings. The repo's passphrase is
generated by the portal and stored encrypted.

On the **backup server**: one `authorized_keys` line you paste yourself, restricting the
client's key to `borg serve` on its own repository only.

This follows the retention split from [BORGMATIC_INTEGRATION.md](BORGMATIC_INTEGRATION.md).
The client config has no `keep_*` settings and is only ever run with `create`; pruning is
done by the portal.

<a id="before-you-start"></a>
## Before you start

1. **The portal can already reach the backup server.** You need an SSH credential on the
   **SSH Credentials** page for the account that holds your repos, with access to the
   folder new repos will go in (e.g. `/srv/backups/haven-backup`). If you set that up per
   [RESTRICTED_SSH_ACCOUNTS.md](RESTRICTED_SSH_ACCOUNTS.md) with
   `--restrict-to-path /srv/backups/haven-backup`, every enrolled repo lands inside that
   path and the portal can monitor and prune it with no further changes.
2. **The portal has an https URL the client can reach.** The install command sends a
   one-time token over the network and receives the repo passphrase back, so the script
   refuses a plain `http://` portal URL unless you add `--allow-http`. Only do that on a
   network you trust.
3. **The portal can SSH to the client as root** (for "Backup now"). The client's sshd must
   allow key-based root login: `PermitRootLogin prohibit-password` (Debian/Ubuntu's default)
   or `yes` (Proxmox's default). With `PermitRootLogin no`, scheduled backups still work but
   "Backup now" won't; the script warns about this.
4. **The repo folder exists on the backup server** and is owned by the backup account.
   Borg creates the repo's own folder but not the folders above it.

<a id="option-a"></a>
## Option A: the one-line install command

1. In the portal, go to **Client Hosts → Enroll a new host** and fill in:
   - **Name**: used for the host, the repo, and the repo's folder (`<repo folder>/<name>`).
     Letters, digits, `.`, `_`, `-`.
   - **Address the portal reaches it at**: hostname or IP, used for "Backup now".
   - **Backup server**: the SSH credential from step 1 above.
   - **Repo folder on the backup server**: an absolute path, e.g. `/srv/backups/haven-backup`.
   - **Folders to back up**: absolute paths, one per line.
   - **Schedule**: a systemd `OnCalendar` expression. The default `*-*-* 02:00:00` is daily
     at 02:00. Check one with `systemd-analyze calendar '<expr>'`.
   - **Retention** and **Stale after**: the same settings as on a repo.
   - **Portal URL the client will use**: pre-filled with the address you're browsing from.
     Change it if the client reaches the portal by a different name.

2. Click **Generate install command**. You'll see something like:
   ```bash
   curl -fsSL https://haven.example.com/api/enroll/install.sh | sudo bash -s -- --portal https://haven.example.com --token 7Kq…
   ```
   **The command is shown only once** and works once, for 60 minutes by default
   (`HAVEN_ENROLLMENT_TOKEN_TTL_MINUTES`). If you lose it, **Revoke** the enrollment and
   create a new one.

   To read the script before running it as root, use the second command shown. It gives
   the same result:
   ```bash
   curl -fsSLo haven-enroll.sh https://haven.example.com/api/enroll/install.sh
   less haven-enroll.sh
   sudo bash haven-enroll.sh --portal https://haven.example.com --token 7Kq…
   ```
   Add `--dry-run` to only run the system checks, without changing anything or using the
   token.

3. Run it on the client. **Success looks like:** a series of `[ok]` lines ending in
   `Timer enabled: <next run time>`, then a block titled **One manual step: allow this host
   onto the backup server** containing a line that starts
   `command="borg serve --restrict-to-repository ...`.

4. On the backup server, append that line to the backup account's `authorized_keys`
   (the script prints a ready-to-paste command). The same line is shown next to the
   enrollment on the portal's **Client Hosts** page, with a Copy button:
   ```bash
   sudo -u haven tee -a ~haven/.ssh/authorized_keys >/dev/null <<'KEY'
   command="borg serve --restrict-to-repository /srv/backups/haven-backup/pve1",restrict ssh-ed25519 AAAA… haven-client@pve1
   KEY
   ```
   Use the account from your SSH credential, not necessarily `haven`. No sshd restart is
   needed.

5. Back on the client, the script has been checking every 15 seconds. Within 15 seconds of
   the paste it prints `Backup server access confirmed`, creates the repo
   (`borg init --encryption=repokey-blake2`), starts the first backup in the background,
   and ends with `Done.`

6. **Save the repo passphrase somewhere outside the portal** (a password manager). Without
   it the archives can't be read, and if the portal's own data is lost this is your only
   copy:
   ```bash
   sudo grep encryption_passphrase /etc/borgmatic/haven.yaml
   ```

<a id="option-b"></a>
## Option B: manual walkthrough (same end state)

This does by hand exactly what the script does, and ends with the same files, units and
portal records. Use it on a distribution the script doesn't support, or to set things up
without piping a script into root. Run everything as root on the client unless noted.

1. **Install the tools** (replace `apt-get` with your package manager elsewhere):
   ```bash
   apt-get update && apt-get install -y borgbackup borgmatic
   borg --version        # must be 1.x
   borgmatic --version   # note it: 1.8+ uses the flat config format below, older uses sections
   command -v borgmatic  # note the absolute path, e.g. /usr/bin/borgmatic
   ```
   **Success looks like:** `borg 1.2.x` (or 1.4.x) and a borgmatic version number.

2. **Create this host's key for the backup server:**
   ```bash
   install -d -m 700 /root/.ssh
   ssh-keygen -t ed25519 -N "" -C "haven-client@$(hostname)" -f /root/.ssh/haven_borg_ed25519
   cat /root/.ssh/haven_borg_ed25519.pub
   ```

3. **Generate a repo passphrase** and keep it for steps 4 and 8:
   ```bash
   openssl rand -base64 32
   ```

4. **Write `/etc/borgmatic/haven.yaml`**, mode 600. For **borgmatic 1.8 or newer**:
   ```yaml
   source_directories:
     - "/etc"
     - "/root"
   repositories:
     - path: "ssh://haven@backup.example.com:22/srv/backups/haven-backup/pve1"
       label: haven
   exclude_caches: true
   encryption_passphrase: "<passphrase from step 3>"
   ssh_command: "ssh -i /root/.ssh/haven_borg_ed25519 -o BatchMode=yes -o StrictHostKeyChecking=accept-new"
   ```
   For **borgmatic older than 1.8** (e.g. Debian 12 / Proxmox 8's 1.7.x):
   ```yaml
   location:
     source_directories:
       - "/etc"
       - "/root"
     repositories:
       - "ssh://haven@backup.example.com:22/srv/backups/haven-backup/pve1"
     exclude_caches: true
   storage:
     encryption_passphrase: "<passphrase from step 3>"
     ssh_command: "ssh -i /root/.ssh/haven_borg_ed25519 -o BatchMode=yes -o StrictHostKeyChecking=accept-new"
   ```
   ```bash
   chmod 600 /etc/borgmatic/haven.yaml
   borgmatic config validate -c /etc/borgmatic/haven.yaml     # borgmatic 1.8+
   validate-borgmatic-config -c /etc/borgmatic/haven.yaml     # borgmatic < 1.8
   ```
   **Success looks like:** `All configuration files are valid` (1.8+) or
   `All given configuration files are valid: /etc/borgmatic/haven.yaml` (older).

5. **Create the systemd units** (use your borgmatic path from step 1):
   ```bash
   cat > /etc/systemd/system/haven-backup.service <<'EOF'
   [Unit]
   Description=Haven Backup: borgmatic create (pve1)
   Wants=network-online.target
   After=network-online.target

   [Service]
   Type=oneshot
   ExecStart=/usr/bin/borgmatic --config /etc/borgmatic/haven.yaml create --stats
   Nice=10
   IOSchedulingClass=idle
   EOF

   cat > /etc/systemd/system/haven-backup.timer <<'EOF'
   [Unit]
   Description=Haven Backup: scheduled borgmatic create (pve1)

   [Timer]
   OnCalendar=*-*-* 02:00:00
   RandomizedDelaySec=15m
   Persistent=true

   [Install]
   WantedBy=timers.target
   EOF

   systemctl daemon-reload
   systemctl enable --now haven-backup.timer
   systemctl list-timers haven-backup.timer
   ```
   **Success looks like:** `list-timers` shows one row with a `NEXT` time.
   No systemd? Use a cron entry instead:
   `0 2 * * * root /usr/bin/borgmatic --config /etc/borgmatic/haven.yaml create --stats`
   in `/etc/cron.d/haven-backup`.

6. **Authorize the client on the backup server:** paste this into the backup account's
   `authorized_keys`, with the public key from step 2, the same as step 4 of Option A:
   ```
   command="borg serve --restrict-to-repository /srv/backups/haven-backup/pve1",restrict ssh-ed25519 AAAA… haven-client@pve1
   ```

7. **Create the repo and run the first backup:**
   ```bash
   export BORG_RSH="ssh -i /root/.ssh/haven_borg_ed25519 -o BatchMode=yes -o StrictHostKeyChecking=accept-new"
   export BORG_PASSPHRASE='<passphrase from step 3>'
   borg init --encryption=repokey-blake2 ssh://haven@backup.example.com:22/srv/backups/haven-backup/pve1
   systemctl start haven-backup.service && journalctl -u haven-backup.service -n 20 --no-pager
   ```
   **Success looks like:** `init` ends with the "IMPORTANT: you will need both KEY AND
   PASSPHRASE" notice, and the journal ends with `Finished haven-backup.service`.

8. **Register it in the portal**, in this order:
   1. **SSH Credentials → add**: name `pve1-portal-access`, hostname = the client's
      address, user `root`, and a **new** private key generated for the portal
      (`ssh-keygen -t ed25519 -N "" -f pve1-portal -C haven-backup-portal@pve1`).
   2. On the client, give that key's public half the forced-command line, so it can only
      run the backup:
      ```bash
      echo 'command="/usr/bin/borgmatic --config /etc/borgmatic/haven.yaml create --stats",restrict ssh-ed25519 AAAA… haven-backup-portal@pve1' >> /root/.ssh/authorized_keys
      chmod 600 /root/.ssh/authorized_keys
      ```
   3. **Client Hosts → Add existing host**: name `pve1`, that credential, config path
      `/etc/borgmatic/haven.yaml`.
   4. **Repositories → add**: name `pve1`, the `ssh://` URL from step 4, the backup
      server's credential, the passphrase from step 3, client host `pve1`, and your
      retention settings.

<a id="checking"></a>
## Checking that it worked

1. On the client, check that the first backup finished:
   ```bash
   journalctl -u haven-backup.service -n 5 --no-pager
   ```
   Expect `Finished haven-backup.service`.
2. In the portal, open **Repositories → `<name>` → Refresh now**. Expect `ok`, 1 archive,
   and a last-archive time a few minutes ago. The dashboard card turns **Healthy**.
3. On **Client Hosts**, pick the repo next to the host and click **Backup now**. Expect a
   `success` run whose log starts with `$ borgmatic --config /etc/borgmatic/haven.yaml create --stats`.
4. The enrollment shows **claimed** on **Client Hosts**. You can **Remove** that record
   once you've pasted the backup server line; the host and repo it created stay.

<a id="rerun"></a>
## Re-running, resuming, and uninstalling

- **Interrupted while waiting for backup server access** (Ctrl+C, SSH dropped, or the
  30-minute wait ran out): re-run the script with no arguments to resume:
  ```bash
  curl -fsSL https://haven.example.com/api/enroll/install.sh | sudo bash
  ```
- **Running it again with a token on an enrolled host** is refused, so a second enrollment
  can't overwrite the first one's config or passphrase.
- **Uninstall** removes the timer, units, `/etc/borgmatic/haven.yaml`, the portal's
  `authorized_keys` line and the state folder. It does not remove the packages, the
  client's key, the repo on the backup server, or the portal's host/repo records:
  ```bash
  curl -fsSL https://haven.example.com/api/enroll/install.sh | sudo bash -s -- --uninstall
  ```
  Then remove the client's line from the backup server's `authorized_keys`, and delete the
  host, repo and `<name>-portal-access` credential in the portal.

<a id="troubleshooting"></a>
## Troubleshooting

| Message | Meaning / fix |
|---|---|
| `Portal refused the enrollment (HTTP 410)` | Token already used, expired, revoked, or mistyped. Generate a new command. |
| `Portal refused the enrollment (HTTP 409)` | A host, repo, or `<name>-portal-access` credential with that name already exists in the portal. |
| `Portal URL is plain http` | Use the portal's https URL, or add `--allow-http` on a trusted LAN. |
| `Still no access after 30 minutes` | The line isn't in the right account's `authorized_keys` yet, or the backup server isn't reachable from the client. Try `ssh -i /root/.ssh/haven_borg_ed25519 haven@backup-host` from the client: `Permission denied (publickey)` means the key isn't in place; borg usage text means it's in place and working. Then re-run with no arguments. |
| `Repository path not allowed` in `/etc/haven-backup/probe.log` | The pasted line's `--restrict-to-repository` path doesn't match the repo URL. Copy the line again exactly. |
| `A repository already exists ... with a different passphrase` | Something is already at that path. The script won't touch it; pick another name or move the old repo aside. |
| "Backup now" fails with `Could not connect` | The client's sshd refuses root key login (`PermitRootLogin no`), or the address in the portal isn't reachable from the portal. |

<a id="security-model"></a>
## Security model

- **The token**: 256 bits of randomness. It's shown once, only its SHA-256 hash is
  stored, it works once, and it expires after 60 minutes by default. The claim endpoint is
  rate-limited like login, and unknown, used and expired tokens all get the same error.
- **What a stolen, unused token gets you**: the ability to register a host under that
  enrollment's name and receive its repo passphrase. It gives no access to the backup
  server, because the key that would reach the backup server is only authorized when
  **you** paste the line, and that line shows the hostname that claimed it
  (`haven-client@<hostname>`). If the hostname isn't the machine you expected, don't paste
  it; revoke the enrollment and delete the records it created.
- **The line you paste on the backup server** is built from the claiming client's public
  key. The portal rejects anything that isn't exactly one well-formed OpenSSH public key,
  so a malicious claim can't smuggle a second, unrestricted key or extra options into it.
  It replaces the client's comment with its own.
- **The portal's key on the client** is forced to run
  `borgmatic --config /etc/borgmatic/haven.yaml create --stats` whatever command it
  requests, with `restrict` (no port/agent/X11 forwarding, no pty). Even with the portal
  fully compromised, that key can't get a shell on the client.
- **The client's key on the backup server** is limited to `borg serve` on its own
  repository. It can't get a shell or reach other hosts' repos.
- **`curl | sudo bash`** runs whatever the portal serves, as root. That's the same trust you
  place in the portal already: it holds every repo passphrase. If you'd rather check, use
  the download-then-run form, or Option B.
- See [SECURITY.md](SECURITY.md) for the portal-wide picture.
